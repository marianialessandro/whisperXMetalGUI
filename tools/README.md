# CLI development with native Metal CTC

Use the checkout's independent `.venv`, CPython 3.12.12 and Torch 2.8.0. No app bundle, packaged runtime or GUI is involved. The original `python -m whisperx` CLI remains available; this separate experiment uses its actual ASR, alignment, diarization and exporters with scoped native CTC hooks.

Build the pinned Torch interop library once:

```bash
mkdir -p .cache/native
.venv/bin/python tools/baseline/mps_storage_probe.py build --out .cache/native/mps-ctc.dylib
```

The command prints the library SHA256. Supply that exact value to a new run:

```bash
.venv/bin/python tools/metal_cli.py --mps-library .cache/native/mps-ctc.dylib --mps-library-sha256 SHA256 --native-report outputs/native-report.json --resident-statistics recording.wav --asr_backend mlx --model small --device mps --language it --output_dir outputs/recording
```

Create `outputs/` first. The report path must be new; it is never overwritten. Other pipeline flags, including `--diarize`, are forwarded to the existing CLI. `--help` describes the experimental options; `python -m whisperx --help` lists the unchanged pipeline options. Use the cache and FFmpeg environment described in the root README for offline runs. Models and native libraries stay local.

This source-only path supports IT/EN alignment on MPS and fails if the native handoff is unavailable. It runs native Metal trellis/backtracking with fused wildcard preparation directly from MPS emission storage. Optional `--resident-statistics` adds resident character statistics, timestamp/word reductions, exact three-decimal rounding and paired nearest interpolation; it requires the `nearest` interpolation method. Original alignability decisions and export formats remain in the existing code. Optional `--seed N` records the diagnostic RNG seed and does not change decoder policy.

The private report records actual native calls, completion timings, shader/library hashes and logical boundary bytes. Timestamp means can share a completion group with bounds; their GPU durations must not be added twice. Zero emission host readback refers to this native CTC handoff only, not all pipeline traffic. The process still uses Python orchestration, CPU metadata/grouping, codec and export work, and CPU portions of community-1. This experiment does not certify full GPU placement, end-to-end quality, speedup or a production backend. A failed run retains a report marked `failed`, with no token, CLI argument list, audio or transcript values.

## Optional native speaker assignment

Build the additional independent C ABI library:

```bash
.venv/bin/python tools/baseline/native_speaker.py --build .cache/native/speaker.dylib
```

To the `metal_cli.py` command add `--diarize --speaker-library .cache/native/speaker.dylib --speaker-library-sha256 SPEAKER_SHA256`, using the hash printed by that build. The existing speaker-assignment implementation remains the default when these flags are absent.

This path performs stable turn ordering, timestamp intersections, per-speaker overlap accumulation, winner selection and optional nearest-turn selection on Metal. Binary64 arithmetic is emulated with integer operations using the existing CTC helpers; it preserves stable tie order and sequential sums without converting timestamps or totals to float32. Only integer speaker choices return to Python. String labels, transcript dictionaries and optional embedding references are retained by the host adapter. Zero-duration intersections are excluded, words without a start remain untouched, and no-match words keep their previous label unless nearest assignment is requested.

The experimental domain is at most 4096 turns and 256 speakers per call, with batches of at most 4096 queries and one million queries per transcript. Timestamps must be finite, nonnegative, ordered within each interval, and at most 2^32 seconds; negative zero and nonzero values smaller than 2^-900 are rejected. Query timestamps support Python binary64-compatible scalars, including the existing native alignment scalar subclasses; float32 query scalars are rejected because their original midpoint policy can differ. No unsupported case falls back to CPU assignment. Stable ranking currently uses quadratic work in the number of turns, bounded by the explicit turn limit; this is a correctness implementation with no speedup claim.

`operations.speaker_assignment` in the private run report records both kernels, actual command-buffer GPU duration, retained buffer capacity, logical uploads and compact label readback bytes. Segmentation, embeddings, clustering and other community-1 operations keep their existing backends; this flag does not move the entire diarization pipeline to GPU.

## Native embedding-normalization primitive

The separate `tools/baseline/native_embedding.py` experiment builds a C ABI library for float32 row normalization, the operation preceding community-1 centroid linkage:

```bash
.venv/bin/python tools/baseline/native_embedding.py --build .cache/native/embedding.dylib
```

Use `NativeEmbeddingNormalization(library_path, library_sha256)` as a context manager and call `normalize(contiguous_float32_matrix)`; it returns a new array and a metadata-only dispatch report. The matrix remains unchanged, including readonly arrays. The primitive can also be connected to the experimental CLI with the optional adapter described below.

The kernel computes squared components, the contiguous NumPy pairwise reduction order, square root and division in one Metal command buffer. Fast math is disabled. The experimental domain is 1–4096 rows and 1–1024 components; finite nonzero components must have magnitude between 2^-32 and 2^32. Zero components and signed zero are supported, but an entirely zero row is rejected because the current primitive has no NaN-output contract. Unsupported dtypes, strided arrays and values outside this domain fail explicitly without CPU normalization. Input validation runs on the host; normalization arithmetic runs on Metal.

Input and normalized output cross the host boundary as float32 arrays. Two retained shared buffers use at most 32 MiB total; initialization, wall time, actual GPU completion time, logical upload/readback sizes and retained capacity are reported separately. Logical bytes are not physical-copy measurements. Tests compare float32 bits with NumPy over reduction boundaries, realistic dimensions, signed zero, extreme supported magnitudes and repeated/threaded calls. The C ABI is also exercised under AddressSanitizer and UndefinedBehaviorSanitizer. Identical results on those cases establish bounded parity evidence; complete numerical-domain certification and end-to-end quality/performance remain pending.

## Optional native VBx statistical updates

## Optional native VBx ELBO arithmetic

Rebuild the binary64 library at a new path and add `--vbx-elbo-arithmetic` with `--vbx-matrix-products` and the library/hash flags. This requires the additive `wxdouble_vbx_elbo` ABI. The pinned adapter replaces exactly the likelihood sum assignment and the final ELBO assignment; `np.log(invL)` stays at its original evaluation point on the CPU. The first native call sums frame log-likelihoods. The second forms `log(invL) - invL - alpha**2 + 1`, reduces it and computes `likelihood + (Fb * 0.5) * regularizer`. Every square, subtraction, addition and multiplication rounds separately. Stopping and warning behavior remain in the original loop.

Signed pairwise reductions reproduce the pinned NumPy 2.2.6 order, including its outer positive-zero accumulator and 8192-element buffered chunks. The primitive and adapter reject a different `np.getbufsize()` setting. Regularizer terms use physical C/F reduction order: an all-Fortran operand set preserves F order; mixed layouts use C order. Terms remain in the existing output buffer until scalar reduction; only the final scalar is read back. The likelihood call executes one kernel and the regularizer/final call executes two kernels in one command buffer.

Frame likelihood vectors support 1..4096 elements. ELBO matrices support 1..1024 speakers and 1..1024 features. Inputs are finite float64, zero or have magnitude in 2^-200..2^200, with strictly positive inverse precision. Unsupported input, changed NumPy reduction-buffer size or missing ABI fails explicitly, with no numerical fallback. Read-only/unaligned input and caller-output aliasing are supported by the C ABI. `--kmeans-clustering-equivalence` requires `--kmeans-potential-library` with its hash and the additive `wxkmeans_same_clustering` ABI. ### Lloyd centroid movement vectors in C++

`tools/metal_cli.py --kmeans-lloyd-center-shifts` requires `--kmeans-lloyd-centroid-updates` and replaces the remaining per-cluster Cython Euclidean-distance calls with one native CPU batch. This is separate from `--kmeans-lloyd-shift`, which reduces the squared movement vector for the original tolerance check. The original stopping decision, inertia, random state and supported single-chunk/nonempty-cluster domain remain unchanged.

The new `wxkmeans_lloyd_center_shifts` ABI accepts two plain C-contiguous float32 matrices of the same shape, 1–256 clusters by 1–1,024 features, with finite magnitudes at most 2^32. Each group computes four separately rounded differences, rounds the second square, accumulates the first/third/fourth squares with explicit float32 FMA, then adds the group to the running total. ### Pinned OpenMP Lloyd inertia in C++

`tools/metal_cli.py --kmeans-lloyd-inertia` requires `--kmeans-lloyd-center-shifts` and a CPU library built with the additive `python -m tools.baseline.native_kmeans_potential --output NEW.dylib --with-inertia` option. Observations/centers must be finite with magnitude at most 2^32, weights finite zero or positive 2^-32..2^32, and labels valid. `single_label=-1` includes all observations; a valid cluster index filters the sum. The shared native squared-distance helper preserves the already verified Cython FMA group/tail order. Readonly/unaligned input and input/output aliasing are supported; unsupported cases fail without a numeric fallback.

### Empty-cluster relocation in the bounded native Lloyd path

`tools/metal_cli.py --kmeans-lloyd-empty-relocation` requires `--kmeans-lloyd-centroid-updates` and uses the new CPU `wxkmeans_lloyd_relocated_centroids` ABI. It extends the single-chunk path to empty/zero-weight clusters, preserving the previous centroid ABI's explicit empty-cluster rejection when the flag is absent. The new primitive accepts 1–256 observations, 1–N clusters and 1–1,024 features, finite float32 observations/previous centers bounded by magnitude 2^32, nonnegative weights in the existing zero/2^-32..2^32 domain and valid int32 labels.

C++ performs sample-order weighted FMA accumulation, identifies empty clusters, computes separately rounded differences/squares with the pinned NumPy pairwise row sum, and selects farthest samples using finite-float32 single-kth introselect adapted from [NumPy 2.2.6 selection.cpp](https://github.com/numpy/numpy/blob/v2.2.6/numpy/_core/src/npysort/selection.cpp). It preserves the reversed partition tail, including ties, weighted donor subtraction/transfers, unchanged labels and ascending averaging/fallback order. When every distance is zero it still computes the selection but skips transfers, matching the reference. It does not replace the selection with sorting or the row sum with the different Cython FMA Euclidean kernel. Neither Python argpartition nor the Cython relocation helper computes this optional path.

The sklearn common binary, NumPy core/argpartition source and default reduction buffer configuration are pinned. All inputs are snapshotted and outputs validated before caller buffers are written; unaligned/readonly input and input/output aliasing are supported, while overlapping output regions fail. Raw diagnostic arrays expose distances and selected indices for verification; report records contain only shapes, counts, source pins and metrics. The shared pairwise header and selection/relocation source digests are included in CPU build metadata and NumPy license attribution is retained.

Reports distinguish `kmeans_lloyd_empty_relocation_path_observed` (the new centroid path ran), `kmeans_lloyd_empty_relocation_observed` (empty clusters occurred), `native_cpu_kmeans_lloyd_relocation_calls` and `native_cpu_kmeans_lloyd_relocated_clusters` (actual transfers). `operations.kmeans_lloyd_empty_relocation` reuses the corresponding centroid-update computation through a shared operation index and zero additional timing/snapshots, avoiding double-counting. A standard clip with no empty clusters can therefore report path calls while empty-cluster observation/transfers remain zero. Multiple-chunk centroid merging remains unsupported; no quality, complete-Lloyd, full-GPU or speedup certification is implied.


### Two original Lloyd chunks, up to 512 samples

`tools/metal_cli.py --kmeans-lloyd-two-chunks` requires `--kmeans-lloyd-empty-relocation`, `--kmeans-lloyd-inertia` and a CPU library built with the additive `--with-two-chunks` build flag. That build flag implies the pinned OpenMP inertia dependency; default and `--with-inertia` builds retain their previous APIs. Separate two-chunk ABIs preserve the legacy 256-sample guards. The new fit limit is 512 observations, with at most 256 clusters and 1,024 features. Three or more chunks fail explicitly.

The implementation retains the original 256-row chunk boundaries and static OpenMP scheduling. Each chunk uses the existing pinned LP64 SGEMM assignment primitive. Centroid accumulation uses one private FMA/weight buffer per original effective iteration worker: one worker accumulates both chunks without resetting its buffer; two workers accumulate one chunk each. The two partials are merged from zero before the shared relocation/averaging stage. Two finite float32 partials commute; the implementation does not generalize this to the nondeterministic three-or-more-partial merge observed in Cython. The requested thread count remains 1, 2 or 12, with the regular-iteration team clamped to the original min(requested, chunk_count). Inertia still uses its original requested team, through a separate 512-sample ABI.

The runtime, static-policy and actual-team guards remain active. Raw assignment and relocated-centroid methods opt into the new ABIs with the additive `n_threads` keyword; raw inertia uses `two_chunks=True`. Inputs are snapshotted and caller outputs remain untouched on validation, worker, provider or team failures. CPU records include chunk size/count, requested/effective/actual threads, two BLAS calls when two chunks are used and worker-partial storage. Shared relocation finalization preserves the existing single-chunk behavior. Reports distinguish `kmeans_lloyd_two_chunks_requested`, `kmeans_lloyd_two_chunks_observed` and `native_cpu_kmeans_lloyd_two_chunk_iterations`; a 42-embedding clip enables the path but observes no two-chunk iteration.

This extends Lloyd, not every optional KMeans++ primitive. Existing resident distance, native upcast-chunk and binary64 product options keep their own 256-row/column guards. The larger-domain fit can use the original initialization arithmetic, the existing native weighted potentials and the compatible precomputed-norm path; it does not silently change batch sizes or fall back from an unsupported optional primitive. GUI, worker and model defaults are unchanged, and no full-GPU, quality or speedup certification is implied.
